# Ревью PR

Один ревьюер, несколько раундов: каждый раунд опирается на предыдущие, а не проверяет всё с нуля.

## Вход

- PR: `<repo>#<N>` — или локальный diff `<repo>` `<база>..<коммит>` (так работает `review-eval`).
- Правила — **только из `main` home**: `git -C <home> fetch -q && git -C <home> show origin/main:review/checklist.md`. Не из рабочей копии и не из ветки PR: изменение не может поменять свою проверку. Ревью PR в самом `home`, который меняет `review/` или этот скилл, — тоже по версии из `origin/main`.

## Шаги

1. **Зафиксировать коммит.** `gh pr view <N> -R tinkoff-trade-strategies-checking/<repo> --json headRefOid,baseRefName,title,body,files`. Ревью относится к этому `headRefOid`.
2. **Контекст.** Описание PR, связанная issue (`Closes #N`) с комментариями, прошлые ревью и ответы на них (`gh pr view <N> --comments`, `gh api repos/<org>/<repo>/pulls/<N>/reviews`): уже исправленное не повторять, нерешённое — проверить снова.
3. **Diff.** `gh pr diff <N>` (или `git diff <база>..<коммит>`). Для каждого изменённого файла можно читать полный текст в worktree на этом коммите.
4. **Триггеры.** Пройди чек-лист и выпиши сработавшие пункты — обычно 3–10. Остальные не проверяй.
5. **Три ловца багов — независимо.** Каждому дай diff, сработавшие пункты и свой фокус; друг друга они не видят:
   - **Л1, инварианты и чек-лист** — каждый сработавший пункт R-*;
   - **Л2, корректность** — граничные случаи, ошибки и коды ответов, пустые и неверные входы, согласованность с соседним кодом, который делает похожее;
   - **Л3, контракты и данные** — API, `.proto`, миграции, утечки (секреты, слепой режим) в ответах, ошибках и логах, тесты: покрывают ли изменение, не ослаблены ли.
   В Claude Code — три субагента параллельно на модели `sonnet` с effort `high` (ловцов много, основная модель дорогая; скептик и итог — на основной); в других агентах — три отдельных прохода с чистым контекстом. Каждая находка: `файл:строка`, что не так, как воспроизвести, предполагаемая важность.
6. **Скептик.** Отдельный проход пытается опровергнуть каждую находку по коду. Остаются только подтверждённые доказательством `файл:строка`. Находка, которую нашли двое из трёх ловцов, проверяется так же — совпадение не доказательство.
7. **Важность.** «Важно», «Мелочь» (не больше пяти), «Было до» — по определениям из чек-листа.
8. **Коммит не сдвинулся?** Снова возьми `headRefOid`. Если в PR запушили новый коммит — ревью устарело: начни с шага 1, учитывая уже найденное.
9. **Публикация.** Комментарий к PR (`gh pr review <N> --comment --body-file …`; свой PR одобрить или отклонить нельзя):
   ```
   Ревью агента · коммит <sha7> · сработали: R-INV7, R-T1, …
   Важно: …        (файл:строка — что и почему)
   Мелочь: …
   Было до: …
   ```
   Нет находок — так и написать, со списком сработавших пунктов.
10. **Важные находки** исправляются до слияния; после исправления — новый раунд с шага 1.

## Не делать

- Не добавлять второго, «более строгого» ревьюера поверх: улучшай этот скилл и чек-лист.
- Не сообщать то, что проверяют CI и линтер, и находки без `файл:строка`.
