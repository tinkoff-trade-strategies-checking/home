# Оценка ревьюера

Проверяем проверяющего: находит ли `pr-review` баги, которые у нас реально были, и не шумит ли на чистых PR.

## Шаги

1. **Кейсы.** `review/eval/cases.md` из `main` home. По умолчанию — набор `test`; набор `tune` — только когда правишь чек-лист.
2. **Подготовка кейса.** `git -C ../<repo> worktree add --detach ../<repo>/.worktrees/eval-<ID> <коммит>`. Diff кейса — `<коммит>^..<коммит>`.
3. **Ревью.** Прогони `pr-review` в режиме локального diff на этом worktree. Ответ кейса ревьюеру не показывай. Сохрани находки трёх этапов отдельно:
   - сырые находки каждого ловца (Л1, Л2, Л3);
   - после скептика;
   - итоговое ревью.
4. **Судья.** Отдельный проход получает только ответ кейса (одно предложение) и находки одного этапа. Засчитывает находку, только если она описывает именно этот баг — не «похожую проблему рядом». Судья не видит код и не правит находки.
5. **Счёт по инцидентам:**
   - найден по этапам: Л1 / Л2 / Л3, после скептика, в итоге;
   - **обнаружим**, если нашли хотя бы двое из трёх ловцов;
   - **потерян**, если ловцы нашли, а после скептика или в итоге его нет — значит, отсеивание теряет найденное.
6. **Счёт по контролям:** сколько «Важно» в итоге. Каждое — кандидат на ложную находку; разбери, правда ли это баг. Если правда — это новый инцидент «Было до», заведи issue.
7. **Уборка.** `git -C ../<repo> worktree remove ../<repo>/.worktrees/eval-<ID>` для каждого кейса.
8. **Результат.** `review/eval/results/<ГГГГ-ММ-ДД>.md`: версия чек-листа и скилла (коммит home), таблица кейсов по этапам, полнота на `test`, ложные «Важно» на контролях, разбор промахов и потерь. Коммит — PR в home.

## Что делать с результатом

- **Промах на небольшом diff** (до ~300 строк) или **обнаружимый, но потерянный** баг — предложи правило в `review/checklist.md` или правку `pr-review`. Триггер должен быть виден из diff. Кейс, по которому написано правило, переносится в `tune`, в `test` нужен новый.
- **Ложные «Важно» на контролях** — уточни правило или требование доказательства, а не отключай пункт.
- Полноту поднимаем, пока улучшение не начинает подгоняться под кейсы: если правило помогает только конкретному кейсу и звучит как его пересказ — это подгонка, не добавляй.
- Сравнивай с прошлым файлом в `results/`: полнота не должна падать после правки чек-листа.
