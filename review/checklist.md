# Чек-лист ревью

Правила для ревью PR в репозиториях проекта. Ревьюер (скилл `pr-review`) читает этот файл **из `main` репозитория `home`**, а не из рабочей копии и не из PR: изменение не может поменять проверку, которая его оценивает. Правки этого файла — отдельным PR в `home`.

Каждый пункт: **триггер** — что видно в diff, **проверить** — что именно, **откуда** — инвариант, решение или инцидент. Ревьюер проверяет только пункты, чей триггер сработал на diff (обычно 3–10), и перечисляет их в начале ревью.

## Важность

- **Важно** — ломает поведение, нарушает инвариант INV-*, утечка данных (секреты, раскрытие слепого режима), несовместимое изменение контракта, тест ослаблен или удалён без причины. Блокирует слияние до исправления.
- **Мелочь** — стиль, имена, упрощения, необязательные улучшения. Не больше пяти на ревью.
- **Было до** — проблема существовала до этого PR. Автора за неё не держим; если важная — предложить отдельную issue.

Утверждение о поведении кода — только со ссылкой `файл:строка` из исходников, а не по догадке из имён. Нет доказательства — нет находки.

## Не сообщать

- То, что уже проверяют CI, линтер и форматтер.
- Сгенерированный код (клиенты из OpenAPI, стабы gRPC), lock-файлы, фикстуры в `testdata/`.

## Как пополнять

Новое правило появляется из промаха: баг дошёл до `main` или нашёлся только у человека. Правило добавляется, если (1) похожая проблема встречалась хотя бы в двух PR или инцидент воспроизводится оценкой ревьюера (`review/eval/`), (2) триггер виден из diff. Правило предлагается PR в `home`, в PR — ссылка на инцидент; сливает человек. Правило, которое полгода не срабатывало или даёт ложные находки, — удалить.
