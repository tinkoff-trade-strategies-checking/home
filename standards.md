# Стандарты кода

Общие для всех репозиториев (решения владельца продукта, 17.11.2026). Стековые стандарты — раздел «Стандарты» в `AGENTS.md` своего репозитория, рядом с конфигами линтера и форматтера.

Что может проверить инструмент — проверяет инструмент: форматтер и линтер в CI, их нарушения не обсуждаются на ревью. Здесь — то, что инструмент не поймает. Новое правило, которое можно автоматизировать, — сразу в конфиг линтера, а не сюда.

## Язык

- Идентификаторы — на английском: код, API, таблицы и колонки, имена файлов.
- Комментарии, документация, сообщения коммитов, описания PR и issue — на русском.

## Ошибки и логи

- Ошибку не глотать: либо обработать осмысленно, либо пробросить. Пустой `catch` — только с комментарием, почему так можно.
- На границе (REST, gRPC) каждая ошибка переводится в явный статус: ошибка входа клиента — `400` / `INVALID_ARGUMENT` / `FAILED_PRECONDITION`, нет данных — `404` / `NOT_FOUND`, недоступна зависимость — `503` / `UNAVAILABLE`. Не оставлять «что-то бросилось → INTERNAL / 500 по умолчанию» для ошибок, которые зависят от входа.
- В текстах ошибок и в логах нет секретов (пароли, токены, URL с учётными данными) — даже если код сейчас вызывается только из тестов: потом он пойдёт в рабочий путь.
- В текстах ошибок и логах, которые могут дойти до клиента, нет данных слепого режима: названия, тикера, реальных дат, рублёвых сумм (INV-7).

## Тесты

- Изменение поведения — с тестом, который падает без этого изменения.
- Код по инварианту INV-* — с тестом этого инварианта; где можно — тест на свойство (генерация входов), а не один пример.
- Тест проверяет поведение, а не повторяет реализацию: ожидаемое значение не считается в тесте той же формулой, что в коде.
- Нестабильный тест не перезапускают до прохождения и не чинят `sleep` и повторами: находят причину или удаляют с объяснением.

## Зависимости и сгенерированный код

- Новая библиотека — только с обоснованием в PR и строкой в разделе «Архитектура» `documentation/decisions.md`.
- Версии зафиксированы: lock-файлы, baseline vcpkg, версии в сборке Gradle.
- Сгенерированный код (TS-клиент API, стабы gRPC) не коммитится — генерируется при сборке.

## Размер и простота

- Одна задача — один небольшой PR: ориентир до ~400 строк кода без тестов. Больше — разбить задачу на sub-issues.
- Нет мёртвого и закомментированного кода, отладочного вывода, `TODO` без номера issue.
- Комментарий объясняет «почему», а не «что»: что делает код, видно из кода.

## Стиль C++ (`core`, `dsl`)

- Стиль LLVM: `clang-format` с `BasedOnStyle: LLVM`, проверка формата в CI.
- Имена по LLVM: типы, переменные и поля — `PascalCase`; функции — `camelCase`; перечисления — `PascalCase`, значения — с префиксом по типу; файлы — `snake_case`. Проверяет `clang-tidy` (`readability-identifier-naming`), сначала в режиме наблюдения.
- Новый код — сразу по LLVM; старый код `core` переименовывается при правке файла, не отдельными массовыми PR.
- C++20; деньги — только `core::Decimal`, без `float`/`double` (INV-6); никаких часов, случайности без seed и обхода hash-контейнеров в расчёте (INV-4).
