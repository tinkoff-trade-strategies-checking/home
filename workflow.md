# Как ведём работу

Правила для людей и ИИ-агентов. Цель — чтобы каждая сессия продолжала работу предыдущей, а не начинала её заново.

Файлы `requirements.md`, `decisions.md`, `invariants.md`, `status.md`, `use-cases.md`, `diagrams/` ниже — в репозитории `documentation` (локально `../documentation/`).

## Где что живёт

| Что | Где | Не здесь |
|---|---|---|
| Задачи, их статус, ход работы, что отвергли | [доска проекта](https://github.com/orgs/tinkoff-trade-strategies-checking/projects/2) и issue в нужном репозитории | не в локальных файлах и не в памяти агента |
| Что строим | `requirements.md`, `decisions.md` | — |
| Как пишем код | `standards.md`, раздел «Стандарты» в `AGENTS.md` репозитория | — |
| Почему так устроено | раздел «Архитектура» в `decisions.md`; обсуждения — ADR-канвасы на Miro | — |
| Что нельзя ломать | `invariants.md` | — |
| Общее состояние проекта, открытые вопросы | `status.md` | — |
| Как устроен конкретный репозиторий | `AGENTS.md` репозитория | — |

## Доска

[Kanban](https://github.com/orgs/tinkoff-trade-strategies-checking/projects/2) — один на все репозитории; карточка — issue из того репозитория, где будет изменение (общие продуктовые задачи — в `documentation`, задачи по окружению агентов — в `home`).

| Status | Значит |
|---|---|
| Backlog | задача записана, но не уточнена |
| Ready | понятно, что делать и когда готово; можно брать |
| In progress | у задачи есть исполнитель (Assignees) и ветка |
| In review | открыт PR |
| Done | PR влит, issue закрыт |

Size (XS / S / M / L / XL) ставим при переводе в Ready. Задача больше L — разбить на sub-issues.

Priority — поле issue на уровне организации (в карточке: Fields → Priority), ставится при создании задачи:

| Priority | Значит |
|---|---|
| Urgent | блокирует начало разработки или работу других — делать сейчас |
| High | нужно до начала соответствующей фичи |
| Medium | нужно, но не блокирует ближайшую работу |
| Low | может подождать |

Через API Priority ставится мутацией GraphQL `setIssueFieldValue` (поле `Priority` организации); `gh project item-list` его не показывает.

Агенту для работы с доской нужен доступ `gh` к проектам: `gh auth refresh -h github.com -s read:project,project`. Полезные команды:

```sh
# карточки в работе и готовые к работе — коротко, без полного JSON доски
gh project item-list 2 --owner tinkoff-trade-strategies-checking --limit 200 --format json \
  --jq '.items[] | select(.status=="Ready" or .status=="In progress") | "\(.status) | \(.content.repository)#\(.content.number) | \(.title)"'
# задача и её ход
gh issue view <N> -R tinkoff-trade-strategies-checking/<repo> --comments
```

## Задача от начала до конца

1. **Взять задачу.** Работа идёт только по issue с доски. Нет issue — сначала создать (шаблон «Задача»), указать ФТ и связанные INV, добавить на доску. Перед стартом прочитать issue целиком, включая комментарии: там ход работы и отвергнутые варианты. Назначить себя и перевести в In progress.
2. **Сориентироваться.** Прочитать ФТ, INV и архитектурные решения (`decisions.md`, «Архитектура»), на которые ссылается задача, и `standards.md`. Найти в коде похожее решение и переиспользовать его, а не писать параллельное. Если задача требует отойти от принятого архитектурного решения — остановиться и предложить изменение явно (PR в `decisions.md` с причиной), а не менять подход молча.
3. **Ветка и worktree.** `sh scripts/worktree.sh start <repo> <тип> <N>` — ветка `<тип>/<N>` от свежего `main` в отдельной папке `../<repo>/.worktrees/<тип>-<N>`; работай только в ней. Так несколько агентов работают в одном репозитории параллельно, не мешая друг другу. Прямой push в `main` запрещён правилами репозитория.
4. **Сделать.** Небольшими шагами; изменение вместе с тестами. Код, касающийся инварианта, — с тестом, который этот инвариант проверяет.
5. **Если сессия кончилась раньше задачи** — оставить в issue комментарий: что сделано, что осталось, какие варианты попробовали и почему отказались, где остановились (ветка, файл). Следующая сессия начинает с этого комментария.
6. **Проверить и открыть PR.** До PR — скилл `verify` (сборка, линтер, тесты, запуск по-настоящему) и строка «Проверено: …» в описании. В описании `Closes #N`, заполненный чек-лист шаблона. Затем скилл `pr-review`; находки «Важно» исправляются до слияния. Подробно — раздел «Проверка».
7. **Закрыть.** Вместе с кодом обновить документы, которые изменение сделало неверными, — по таблице ниже, в том же PR.
8. **После слияния.** Ветка на GitHub удаляется сама; `sh scripts/worktree.sh clean` убирает локальные worktree и ветки влитых PR.

## Код, коммиты, PR

Решение владельца продукта, 02.11.2026 (#14).

- Идентификаторы — на английском: код, API, таблицы и колонки БД, имена файлов. Комментарии в коде, документация, сообщения коммитов, описания PR и issue — на русском.
- Сообщение коммита: первая строка — что сделано, по-русски, без префиксов Conventional Commits (`feat:`, `fix:` и т. п.), до 72 символов; при необходимости — пустая строка и пояснение.
- Первый коммит в пустой репозиторий — напрямую в `main` (ruleset пропускает создание ветки), всё дальнейшее — только через PR.
- Ветка — `<тип>/<N>`, где `N` — номер issue в этом репозитории, тип — `feat` (новое), `fix` (исправление), `docs` (документы), `chore` (CI, зависимости, настройки, рефакторинг, тесты). Одна issue — одна ветка — один PR; задачу, которую надо делать параллельно, делить на sub-issues. Пример: `feat/42`.
- `main` защищён во всех репозиториях (ruleset `main`): только через PR, без force-push и удаления, обязательного одобрения нет — агенты вливают PR сами после зелёного CI; где CI есть, его проверки обязательны после режима наблюдения: сейчас `core` — `build-test`, `docker-image`, `style`, `frontend` — `check`. Добавили CI в репозиторий — добавь его проверки в ruleset (Settings → Rules).
- Слияние — только squash (merge commit и rebase выключены): заголовок итогового коммита = заголовок PR, тело = описание PR. Поэтому заголовок PR пишется по правилу коммитов выше. Ветка удаляется после слияния автоматически.
- Вливать командой `gh pr merge --squash --auto`: PR вольётся сам, когда обязательные проверки пройдут, — агенту не нужно ждать CI. Если GitHub отвечает «clean status» (обязательных проверок нет и PR уже готов), вливать без `--auto`: `gh pr merge --squash`.
- Шаблоны issue и PR — общие для организации, в репозитории `.github` (`../.github`); в отдельных репозиториях своих шаблонов не заводим.

## Когда обновлять документы

Документ правится в том же PR, что и изменение, которое сделало его неверным. «Потом» не наступает.

| Что изменилось | Что обновить |
|---|---|
| Команда сборки, запуска, тестов, линтера | раздел «Команды» в `AGENTS.md` репозитория |
| Новая папка, модуль, слой, точка входа | раздел «Структура» в `AGENTS.md` репозитория |
| Новый компонент или связь между компонентами (модуль Spring Modulith, gRPC-метод, хранилище) | `architecture.md` |
| Архитектурный выбор: библиотека, протокол, формат контракта, способ хранения | раздел «Архитектура» в `documentation/decisions.md`, в том же PR |
| Решён вопрос из `status.md` или помеченный «Вопрос» / «Допущение» в `use-cases.md` | `decisions.md` (или `requirements.md`, если меняется ФТ); убрать вопрос из `status.md` и `use-cases.md` |
| Поведение фичи разошлось с юзкейсом | UC в `use-cases.md` и диаграмма в `diagrams/` |
| Появился или изменился инвариант, его проверка в тестах или CI | `invariants.md`, колонка «Проверка» |
| Агент дважды ошибся из-за правила, которого нигде нет | `AGENTS.md` репозитория; если правило общее для всех репозиториев — `AGENTS.md` в `home` |
| В репозитории появился первый код (каркас) | слой проверки — раздел ниже, в том же PR или сразу следующей задачей High |
| Появился, переименован или архивирован репозиторий | в `home`: раздел «Репозитории» в `AGENTS.md`, `REPOS` в `scripts/clone-repos.sh` и `scripts/worktree.sh`, `additionalDirectories` в `.claude/settings.json`, команда Codex с `--add-dir` в `README.md` и `AGENTS.md`; на GitHub — только squash, удаление веток после слияния, ruleset `main` |
| Скилл нужен в нескольких репозиториях | один экземпляр в `home/.agents/skills/`, переходник в `home/.claude/skills/`, запрет переходника в `home/opencode.json` |
| Указание в любом `AGENTS.md` оказалось неверным или пришлось выяснять то, что пригодится следующей сессии | исправить или дописать в той же задаче (`home/AGENTS.md`, раздел «Поддержание контекста») |
| Закрыта веха, сдвинулся срок, решено что-то на синке | раздел «Где мы» и сроки в `status.md` |
| ADR-канвас на Miro изменён командой | итог — в раздел «Архитектура» `decisions.md` |

Если документ расходится с кодом и неясно, что верно, — не выбирать молча: сообщить в PR или issue и спросить команду.

## Проверка

Как устроена — `review/README.md`. Правила:

- **Изменение запускают, а не читают.** Сначала дешёвое (линтер, сборка, тесты области), потом дорогое (весь набор, сквозной сценарий) — до PR, а не в CI. Команды — в `AGENTS.md` репозитория, порядок — скилл `verify`.
- **Отметка в PR.** В описании строка `Проверено: <что запускал> — <результат>` или `Проверено: нет — <причина>`. Она попадает в коммит squash-слияния; непроверенные изменения ищутся по ней (`scripts/review-stats.sh`).
- **Три попытки.** Проверка падает три раза подряд — агент останавливается, пишет в issue вывод и что пробовал, и зовёт человека.
- **Нестабильный тест** не перезапускают до прохождения, не чинят `sleep` и повторами, не ослабляют. Нашёл причину — чини; не нашёл — удали тест и запиши в PR почему.
- **Ревью** — скилл `pr-review`: правила из `review/checklist.md` в `main` home, три независимых ловца багов, скептик, «Важно / Мелочь / Было до». Ревью относится к коммиту: запушили новый — ревью заново. Не наращиваем число ревьюеров — улучшаем этот.
- **Проверки пишут владельцы кода.** Владельцы — в `.github/CODEOWNERS` репозитория; PR, меняющий тесты инвариантов и CI, автоматически зовёт владельца. Пока это уведомление, а не обязательное одобрение.
- **Новая обязательная проверка — сначала в режиме наблюдения.** Барьер на `gh pr create` (`.claude/hooks/verify_gate.py`), новая проверка CI в ruleset, новое правило чек-листа: сначала смотрим, что она бы заблокировала, разбираем ложные срабатывания, потом включаем.
- **Промахи → правила.** Баг дошёл до `main` или нашёлся только у человека — новый кейс в `review/eval/cases.md` и, если триггер виден из diff, правило в `review/checklist.md` (порядок — там же, в «Как пополнять»).
- **Проверяем проверяющего.** Раз в месяц и после правки чек-листа или `pr-review` — скилл `review-eval` и `scripts/review-stats.sh`: полнота на реальных багах, ложные «Важно» на контрольных PR, откаты и отклонённые PR.
- **Чистка.** Раз в месяц вместе с оценкой — убрать правила, которые не срабатывали и не ловили ничего, и тесты, которые ничего не проверяют. Правила и тесты не должны только расти.

## Слой проверки репозитория

Как только в репозитории появляется код (каркас Angular, Spring, CMake и т. п.), тот же агент в том же или сразу следующем PR заводит:

1. **Команды** в `AGENTS.md` репозитория: установка, сборка, линтер, тесты, запуск. По ним работает скилл `verify`.
2. **CI** (`.github/workflows/`): линтер, сборка, тесты на PR и на основной ветке.
3. **Обязательные проверки** в ruleset `main`: сначала CI работает без обязательности (наблюдение), после нескольких зелёных PR без ложных падений — проверки CI добавляются в ruleset.
4. **`.github/CODEOWNERS`**: владелец тестов и CI.
5. **Задачи** на сквозной сценарий и тесты на свойства для инвариантов этого репозитория, если их ещё нет на доске.

`scripts/project-health.py` находит репозитории, где чего-то из этого не хватает.

## Как проект направляет работу

- **Начало сессии без задачи** — скилл `next`: подтянуть репозитории, `scripts/project-health.py`, завести задачи на пробелы без дублей, выбрать следующую задачу.
- **По ходу любой задачи** — заметил, чего не хватает проекту (проверки, команды, правила, документа, скилла), — заведи задачу или исправь сразу, если мелко. Чего-то не видит `project-health.py` — допиши в него проверку.
- **Раз в месяц** (или перед синком команды) — цикл самосовершенствования: `next` → `context-audit` → `review-eval` → `scripts/review-stats.sh` → чистка правил и тестов, которые ничего не ловят. Итог — задачи на доске и PR в `home`.

## Готово, когда
- `verify` пройден, в PR есть строка «Проверено: …»;
- тесты и линтеры проходят, CI зелёный;
- после `pr-review` нет нерешённых «Важно»;
- инварианты не нарушены, а затронутые покрыты тестами;
- документы соответствуют коду;
- PR одобрен человеком и влит, issue закрыт.

## Чего не делать
- Не переписывать работающий код без задачи на это: рефакторинг — отдельная issue с причиной.
- Не переоткрывать решённое: архитектурное решение и закрытый вопрос меняются только явно — PR в `decisions.md` с причиной.
- Не дублировать знания: правило живёт в одном месте, остальные ссылаются на него по ID.
- Не держать важное только в чате, локальных заметках или памяти агента: следующая сессия и коллеги этого не увидят.
